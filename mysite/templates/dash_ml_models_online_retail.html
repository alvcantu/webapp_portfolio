ML Predictions Dashboard

Predicting sales for an online retail business using historical transaction data with XGBoost machine learning regression algorithm.

Select a model to view its description and my approach to the problem.

I chose XGBoost for all models because of its high performance and focus on improving performance by changing the feature engineering rather than the model. The algorithm works by building decision trees (i.e. a series of questions that lead to the optimal prediction by reducing the difference between actual values and predicted values, or the residuals) sequentially. Testing the performance on one and then based off the reduced residuals creating an improved one, 'gradient boosting' in fancy terminology. But given XGBoost is EXTREME gradient boosting, it calculates its trees in a unique way by figuring out where is best to split the data. In the case of InvoiceDate, it smartly determines whether 'Is the day before or after Thursday?' OR 'Is the day before or after FRIDAY?' is a better question for reducing the residual by testing each of these scenarios out. It’s like a team of weak students, each correcting the mistakes of the previous one, gradually improving their collective score to become top performers, each 'student' here being a decision tree. Eventually after many different combinations it picks the most helpful questions that reduces the residuals the most by minimising the Root Mean Square Errors or RMSE (a measure showing the average magnitude of errors). Hence leading to the most accurate prediction.

Since the sales models below are meant to predict sales at a transaction level of granularity, I first built a model to predict how many transactions there will be per day solely based on date columns (or features in fancy ML language) and training it using all the transactions in the dataset. This way I can run the predictions without any additional data point besides the invoice date. The settings for this model were chosen using 150 iterations of Bayesian Optimization. It works by learning from its mistakes. It smartly mixes testing known good settings (exploitation) with scouting new settings (exploration) using probability theory, ensuring we efficiently choose the best settings for our machine learning model.

The first model to predict sales I built using XGBoost and RandomizedSearchCV: This model was trained on the entire dataset. I made the mistake of including the exact quantities sold and prices in my model, which directly calculate sales. This made the model too good at predicting training data but poor at generalizing to new data, a problem known as overfitting. I only included Year, Month and Day as date features, in retrospect I could’ve added many more features from the InvoiceDate column. To ensure my model could handle changes over time, like seasonal trends, I split my data in a way that respects time order. I used a technique called TimeSeriesSplit, which cross validates the results so a sample of data gets tested with training data. I chose 3 splits as its rule of thumb to use 3-5. In order to find the best settings for my model I used RandomizedSearchCV technique. It works by choosing different random combination of settings for the model and tests the results against one another, eventually the best one is chosen. Think of it like trying on different clothing outfits to see which one fits best when you look in the mirror, but instead of outfits, we're trying different model settings, and we do this multiple times to ensure we find a good match. I did 30 different rounds of 30 different outfits. The model proved worthy when looking at performance metrics but useless when applying it to new data because of the previously mentioned mistake.

The second model to predict sales is also built using XGBoost but the settings are chosen with a Bayesian Optimization technique instead. Unlike the first, I did not include deterministic features like Quantity and UnitPrice. I expanded the features based on InvoiceDate so now the model is trained on Quarters and Season which can help with yearly sales fluctuations. Like the first, I also used TimeSeriesSplit with 3 rounds of splits. I used Bayesian Optimization as, unlike RandomizedSearchCV technique, it learns from its mistakes. The performance metrics suggest this model is worse that the first one, but given this was not trained on deterministic features that is expected. When applying to future the data there seem to be less fluctuation is sales as compared to actual, which suggest this model is not very good at estimating days of high or low sales. Suggesting additional features need to be added.

The third model adds new features to the model training such as: "IsHoliday", which determines if an invoice date is holiday by its associated country. "Continent" from Country column. "Description" of the item being transacted. Fiscal dates associated from the invoice date. Categorises StockCode's such as those that are fees like 'AMAZONFEE' or 'BANK CHARGES', those that are gift cards that start with 'gift', those are postage 'POST' or 'DOT', and those 'party bags that start with 'DCGSS'. Also classify the StockCode's according to their length. Given its high performance last time, I stuck with Bayesian Optimization but incremented the number of iterations (how many settings it tests)for the model from 25 to 75. Performance metrics are mostly the same as the second model with the exception of Mean Absolute Percentage Error or MAPE and the average % difference between actual and predicted values, suggesting the model is better at handling outliers such as returns or very high sales dates. When applying the model to future data, the results are lower than the second but also less dispersed.

Given the third model demonstrated that it is possible to reduce MAPE by a significant amount and given MAPE measures the differences between actual and predicted in relative terms rather than absolute, for the fourth model I decided to use MAPE as a loss function (I.e. minimise it rather than RMSE. In retrospect minimising this measure is more appropriate given sales amount can vary by a lot from transaction to transaction, so having accurate predictions in % or relative terms is more important. I stuck with the same features as the third and same # of iterations of Bayesian Optimization at choosing ideal settings.
