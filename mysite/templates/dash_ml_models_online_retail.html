ML Predictions Dashboard (WIP)

All models are meant to predict sales for an online retail business using historical transaction data.

Select a model to view its description and my approach to the problem

Since the sales models are built to predict sales at a transaction level of granularity, I first build a model to predict how many transactions there will be per day. Hence I build a model based solely on date features and train it using all the transactions in the dataset. This way I can estimate the number of transactions per day without any additional data point. I chose XGBoost because of its high performance. It works by building decision trees (i.e. a serious of questions that lead to the optimal transactions amount) sequentially, testing the performance on one and then based off that creating an improved one, 'gradient boosting' in fancy terminology. It’s like having a team of experts where each new expert learns from the mistakes of the previous ones. Each 'expert' here is a decision tree, which makes decisions based on questions like 'Is the day a weekend?' or 'Does the day belong to Winter/Spring or Summer/Autumn?'. Each tree works is categorised by its usefulness in predicting the transaction count and all together help to produce an accurate amount. I chose to optimise it to minimise the root mean squared error as that measures how much its predictions differ from actual transaction count.

First model to predict sales I built using XGBoost and RandomizedSearchCV: This model was trained on the entire dataset. I made the mistake of including the exact quantities sold and prices in my model, which directly calculate sales. This made the model too good at predicting training data but poor at generalizing to new data, a problem known as overfitting. I only included Year, Month and Day as date features, in retrospect I could’ve added many more features from the InvoiceDate column. To ensure my model could handle changes over time, like seasonal trends, I split my data in a way that respects time order. I used a technique called TimeSeriesSplit, which cross validates the results so a sample of data gets tested with training data. I chose 3 splits as its rule of thumb to use 3-5. In order to find the best settings for my model I used RandomizedSearchCV technique. It works by choosing different random combination of settings for the model and tests the results against one another, eventually the best one is chosen. Think of it like trying on different clothing outfits to see which one fits best when you look in the mirror, but instead of outfits, we're trying different model settings, and we do this multiple times to ensure we find a good match. I did 30 different rounds of 30 different outfits. The model proved worthy when looking at performance metrics but useless when applying it to new data because of the previously mentioned mistake.

The second model to predict sales is also built using XGBoost but the hyperparemeters are chosen with BayesianOptimization. Unlike the first I did not include deterministic features like Quantity and UnitPrice. I expanded the features based off InvoiceDate so now the model is trained on Quarters and Season which can help with yearly sales fluctuations. I also used TimeSeriesSplit with 3 rounds of splits and minimised the Root Mean Squared Error or RMSE. I used Bayesian Optimization as, unlike RandomizedSearchCV technique, it learns from its mistakes. It smartly mixes testing known good areas (exploitation) with scouting new territories (exploration) using probability theory, ensuring we efficiently zoom in on the best settings for our machine learning model.The performance metrics suggest this model is worse that the first one, but given this was not trained on deterministic features that is expected. When applying to future the data there seem to be less fluctuation is sales as compared to actual, which suggest this model is not very good at estimating days of high or low sales. Additional features need to be added.
