Stocks data mart

My intention with this project is to keep track of all trillion dollar company stock prices every day and forecast prices for the next 5 trading days. All with quality checks in place.

The project's first step is to extract all ticker symbols for trillion dollar companies. I get this data from wikipedia, first scraping the wiki page for each company and then extracting the ticker symbol.

{{ company_list_spider }}

Then, using the yfinance library, I extract information about each company using the newly acquired tickers and ingest them to dimenions table ST_DimCompany in my database.

{{ etl_ST_DimCompany }}

I then use the newly created table (with quality checks already in place) to extract each ticker again and incrementally add the latest prices to table ST_FactPrices.

{{ etl_ST_FactPrices }}

I then add a forecasts to my model. An ARIMA model fills in a new forecast_price_arima column for the next few 5 trading days for each company.

{{ etl_ST_FactPrices_Forecast }}

Once all prices are generated and validated, I generate automatic pdf's that place these neatly in a professional way.

{{ pdf_gen_stocks }}

Finally I create a script that's sole purpose is to run the correct jobs in order as I've just shown you. This script is later placed in a CRON job scheduler so it runs daily, capturing new prices and calculating forecasts automatically. If the process fails I get an email informing me of what went wrong.

{{ run_stocks }}

All of this is rendered to this HTML dashboard using chart.js for all the visuals and interactions

{{ dash_stocks }}

South Park data mart

My intention with this project was to learn web scraping and making a relational data model with quality controls that updates itself.

The project involves scraping data from Wikipedia. So I create two spiders that extract episode and character information.

Here is the episode spider:

{{ episodes_details_spider }}

Here is the character spider:

{{ character_details_spider }}

Once the spiders extract data from the web, they save it to a csv. I then transform the csv to clean the data, take care of special cases, and create a character_id.

{{ etl_stg_southpark }}

Once character_id is added I use it to loop through all the episode Wikipedia URL's I extracted previously to obtain the episode summary and if those charater_id's appear in the article. I assume that if the character_id appears, then they appear in the episode too, which is not correct :( my personal south park knowledge knows best. But I did it as a fun exercise and it is somewhat close.

Here is the third spider that loops through all the episode url's:

{{ episode_loop_spider }}

I transform and normalize all the data, add quality checks and load it into mySQL database in a relational model form withh additional quality constrains, with a fact table listing characters per episode and two dimension tables listing details on episodes and characters respectively.

{{ etl_southpark }}

Finally I create a script with the sole purpose of running the jobs in correct order. This script is later placed in a CRON job scheduler so it runs daily, thereby capturing new episodes and new characters automatically. If there are any failures, the script sends me an email informing me of what went wrong.

{{ run_southpark }}

All of this is rendered to this HTML dashboard using chart.js for all the visuals and interactions

{{ dash_southpark }}

Parking and bike spots in CDMX

The aim of this project was to build a data pipeline using GeoJSON. The goal is to plot all bike stations and parking meters in Mexico City, the ones with publicicly available data.

Data for this project comes from 'Portal de Datos Abiertos de CDMX', containing data for ONLY SOME neghbourhoods of the city.

Bike stations data: https://datos.cdmx.gob.mx/dataset/ubicacion-de-estaciones-de-ecobici-sistema-anterior

Parking meter data: https://datos.cdmx.gob.mx/dataset/infraestructura-de-parquimetros

First step was to create a staging file with the number of bike stations per neighborhood (done by counting each row in the dataset and grouping them) and the approximate area of the neighborhood for later metric calculations (done by calculating the perimeter using the Haversine function which computes the distance between two coordinate points).

{{ stg_area_bikestations_percolonia }}

Next step was to create another staging file with the parking meters per neighborhood, but given the GeoJSON does not contain neighbourhood information I joined the data according to coordinates with the bike CSV.

{{ stg_parking_percolonia }}

Final step of the pipeline is to join the two staging files into one file with shared neighborhood information.

{{ final_bikestations_parking_percolonia }}

Then its all rendered to this HTML dashboard with a map and table of the previously computed metrics

{{ dash_cdmx }}

How app was created

Main Flask python script

This main file applies all backend logic for all aspects of the app. Each app route @ represents each button or url of the app

For this documentation, all text boxes with code on this site are automatically rendered with senstive data such as passwords and API keys being hidden or 'sanitized'. The database schema diagram is automatically created with the create_data_structure_diagram function using graphviz library.

For the data dashboards, note how a SQL query is executed that dynamically changes depending on user input. This results in only the data the user needs to see to be loaded to the site, hence reducing the need for additional front-end javascript logic.

{{ web_app }}

Data 'Google'

As shown in the flask @dash_data_google section above, I run a query to extract the information schema of each table in the database automatically (with comments of each column for added context) and include it in the prompt for the large language model to understand the data and output an accurate SQL query. This query is then executed, the results are cleaned/converted, and the output is rendered to the user interface. The 'Table' option has the ability to export to CSV, Excel, PDF etc. While the other visual options generate a Chart.js, the data is pre-processed in the backend as well. I use OpenRouter auto selector so the best LLM is chosen every time. For safety purposes, I make sure to only execute queries that do not modify the database in any way.

This script is the front-end HTML for the self-service. It is used to collect user input and send it to the back-end.

{{ dash_data_google }}

Auto-generated presentation

This script generates the daily presentation. I use a master canvas so the presentation remains consistent throughout and add elements afterwards. Graphs (from matplotlib) and bullet points (from LLM response) are both always generated using latest data. This file is also placed on a CRON job scheduler so it runs every day, generating a new presentation automcatically.
